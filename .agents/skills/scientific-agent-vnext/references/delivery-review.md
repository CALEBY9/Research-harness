# 交付检查与作者可用性

先检查正文，再看过程记录。可读的诊断、成功运行的脚本和一份 PASS 报告都不能代替请求的正文。

## 两个独立评价维度

可信性检查关注数字、来源支持、研究范围、比较条件、因果强度、方法执行身份和图文口径。新增、实质改变或高风险论断必须回到相关原文或项目结果。引用存在核查与语义支持核查分别记录。没有核查就标为未核查。

可用性检查关注读者能否跟上问题推进，章节是否完成承诺，最近工作比较是否实质准确，段落是否充分展开，作者是否需要重写。来源无误但正文无法使用，仍属于写作失败；作者喜欢的文字若改变研究含义，也不能通过。

## 有限修订

第一次审读定位最影响可用性的具体段落，完成针对性修复。第二次仅处理仍存在的问题及修复引入的连带冲突。不按模型分数无限迭代，不增加礼仪性 reviewer 数量。

同一模型在同一上下文中的审读称为自查。新上下文的同模型审查仍可能共享偏差，不能称为独立专家审稿。确有授权和运行条件时，给另一审查上下文提供当前稿、必要原始证据与作者范围；不提供写作者先前的自我辩护或预设高分。跨提供方调用先确认内容传输权限。

## 正式交付

正文放在首位。伴随说明简要给出实质改动、科学边界是否保持、实际完成的核查与待解决事项。来源已有账本时更新相关条目，不建立重复体系。普通小任务没有必要生成 run manifest、哈希清单、状态机和多份验收表。

如果稿件仍有局部待核查内容，清楚称为审阅稿，不能报告投稿就绪。受保护原稿只在明确授权下替换；对照试写放在独立输出位置。

## 为什么保留人工验收

作者最终选择的是能用的稿件。记录作者实际修改用时、需要重写的段落、漏掉的关键证据和科学错误，比代理自评更加贴近本任务目标。人工选择不免除事实检查；两者都需要。
